# เรียนรู้จาก Support Ticket Triage Agent ที่รันได้

โปรแกรมนี้รับเรื่องร้องเรียน อ่านประวัติและเอกสาร แล้วเสนอระดับความเร่งด่วน วิธีส่งต่อ และข้อความตอบ โดยยังไม่ส่งข้อความหรือแก้ระบบจริง ทุกข้อเสนอรอคนอนุมัติ

## ใช้อะไร และเลือกเพราะอะไร

| ส่วน | สิ่งที่ใช้ | เหตุผลในขอบเขตงานนี้ |
|---|---|---|
| ภาษาและตัวรัน | Python 3.11+ และ console CLI | โจทย์รับ console ได้ จึงทดสอบระบบได้โดยไม่ต้องสร้างเว็บก่อน |
| สัญญาข้อมูล | Pydantic 2 | ตรวจชนิดข้อมูลและค่าที่อนุญาต พร้อมสร้าง JSON Schema จากโมเดลเดียว ลดการเขียนสัญญาซ้ำ |
| โมเดล | OpenAI GPT-4.1 mini ผ่าน Responses API | รองรับ flow เรียกเครื่องมือและคำตอบตาม schema ที่โปรเจกต์ใช้ ผู้ประเมินเปลี่ยน key/model ผ่านการตั้งค่าได้ |
| Agent orchestration | loop ที่เขียนใน agent.py | มีเพียงสามเครื่องมือกับจำนวนรอบที่จำกัด จึงอ่านและอธิบาย flow ได้โดยตรง ยังไม่จำเป็นต้องเพิ่ม LangChain/LangGraph |
| การเรียก API | urllib ของ Python | ลด dependency สำหรับโปรเจกต์เล็ก แลกกับการเขียน transport, timeout และ retry เอง ซึ่งต้องทดสอบ |
| แหล่งข้อมูล | JSON mocks และ lexical KB search | โจทย์ยอมรับ mock สี่เอกสารยังตรวจผลค้นได้ง่าย ไม่มี payment DB หรือ production telemetry จริง |
| การตรวจ | unittest และ rubric สามเคส | แยกการตรวจพฤติกรรมโปรแกรมจากคุณภาพคำตอบโมเดล แล้วอ่านผลจริงด้วยคนอีกชั้น |

ดังนั้น “framework ที่ใช้” ตอบได้ว่าเป็น Python application ใช้ Pydantic สำหรับข้อมูล และเขียน bounded agent loop เอง ไม่ควรบอกว่าใช้ framework ที่ไม่มีในโค้ด หากระบบโตจนต้องมีหลายขั้นที่พักแล้วทำต่อได้ ค่อยประเมิน framework สำหรับ workflow และ persistence จากความต้องการจริง

เส้นทางข้อมูลคือ ticket ทั้งบทสนทนา → GPT ขอเรียก tool → Python ตรวจและเรียก tool → ส่งผลกลับ GPT → ได้ decision JSON → Python ตรวจ → ได้ข้อเสนอรอคนอนุมัติ จุดที่ GPT ขอเรียก tool กับจุดที่โปรแกรมยอมให้เรียกจึงแยกจากกัน

## เริ่มจากรันก่อน

บนเครื่องนี้ เปิด terminal ในโฟลเดอร์โปรเจกต์แล้วรัน:

```powershell
& .\run.ps1 -Mode demo
```

เครื่องอื่นใช้วิธีสร้าง virtual environment และติดตั้งตาม README ได้ โหมด demo ใช้คำตอบจำลองเฉพาะสามเคสในโจทย์ แต่เรียกฟังก์ชันเครื่องมือและตรวจผลลัพธ์จริง จึงช่วยเรียนรู้ flow ได้โดยไม่มี API key อย่าใช้ผล demo เป็นหลักฐานว่า GPT วิเคราะห์ได้ถูกต้อง

ตัวเปิดโปรแกรมตรวจ Python ผ่าน scripts/check_runtime.py แทนการส่งโค้ดเป็น argument ของ -c เพราะการส่งเครื่องหมายคำพูดให้โปรแกรมภายนอกต่างกันตามโหมด PowerShell หาก interpreter ใช้ไม่ได้จะลองตัวถัดไป การแสดง stderr ของตัวโปรแกรมทำเป็นข้อความอ่านง่ายพร้อมรักษา exit code โดยไม่เปลี่ยน execution policy ของเครื่อง

หากข้อความไทยกลายเป็นตัวอักษรแปลก แต่โปรแกรม completed อาจเป็นปัญหาการถอดรหัสข้อความระหว่าง Python และ PowerShell Python ส่ง UTF-8 ตัวเปิดโปรแกรมจึงตั้ง encoding ที่ใช้รับ output ให้ตรงกันชั่วคราวแล้วคืนค่าเดิม การเขียนไฟล์ JSON ใช้ UTF-8 โดยตรง จึงเป็นคนละขั้นกับการแสดงผลใน terminal

เริ่มดูเคส Enterprise เพียงเคสเดียวได้ด้วย:

```powershell
& .\run.ps1 -Mode demo -TicketId ticket-002
```

## หนึ่ง Ticket มีหลายข้อความ

เปิด `data/tickets.json` แล้วดู ticket-003 ข้อความแรกถาม dark mode แต่ข้อความที่สามแจ้งว่า System Default ไม่ทำงาน และข้อความล่าสุดขอฟีเจอร์ตั้งเวลา หากอ่านเฉพาะข้อความล่าสุด ระบบอาจพลาดปัญหาที่ยังไม่จบ

ใน `models.py`, `Ticket.messages` จึงเป็นรายการข้อความเรียงตามลำดับ พร้อม time_label โดยเก็บเวลาตามต้นฉบับ ไม่สร้างวันที่จริงที่ไม่มีในโจทย์

ลองคิดก่อนเปลี่ยนโค้ด: ถ้าลูกค้าบอกในข้อความถัดไปว่า “ตอนนี้ธีมทำงานแล้ว เหลือแค่ขอตั้งเวลา” ระบบควรประเมินตามปัญหาใดที่ยังไม่จบ?

## สัญญาข้อมูลช่วยให้โปรแกรมใช้ผลของ AI ต่อได้

`Ticket` กำหนดรูปแบบข้อมูลเข้า ส่วน `Decision` กำหนดข้อมูลออก เช่น urgency, issue_types, sentiment, evidence, suspected_causes, unknowns, recommended_action และ draft_reply

ตัวอย่างแนวคิด: หากลูกค้ารายงาน error 500 นั่นเป็น customer_report หากเครื่องมือตรวจพบสถานะบริการปกติ นั่นเป็น service_status ทั้งสองข้อมูลอาจขัดกัน ต้องเก็บไว้ ไม่เปลี่ยนเป็นข้อสรุปว่าลูกค้าเข้าใจผิด หรือระบบถูกแก้แล้ว

`Literal` จำกัดค่าที่ใช้ได้ เช่น urgency ต้องเป็น critical/high/medium/low การตรวจ schema ป้องกันรูปแบบผิด แต่ไม่ได้รับประกันว่าเหตุผลหรือข้อเท็จจริงในประโยคถูกต้อง

`ApprovedPolicy` อยู่แยกจาก `Decision` และมีค่า pending_human_approval โค้ดเป็นผู้เพิ่มส่วนนี้หลังตรวจผล AI จึงไม่เปิดให้ AI อนุมัติข้อเสนอของตัวเอง

แบบฝึกจากโค้ด: หาก AI เพิ่ม approval_required=false เข้าไปใน Decision จะเกิดอะไรขึ้น? ลองอ่านการตั้งค่า extra="forbid" และการรับมือ validation failure ใน agent.py ก่อนดูชื่อ test ที่เกี่ยวข้อง

## เครื่องมือคือฟังก์ชันที่เรียกได้จริง

เปิด `tools.py` จะเห็นทั้ง schema และ implementation

- get_customer_history รับ customer_id แล้วอ่านข้อมูลลูกค้า ระบบยอมรับเฉพาะ ID ของ ticket ปัจจุบัน
- search_knowledge_base รับ query และ limit แล้วคืนเอกสารที่เกี่ยวข้องพร้อม IDs
- check_service_status รับ region แล้วคืนสถานะจำลอง พร้อมบอกขอบเขตของข้อมูล

ทุกผลมี ok เพื่อแยกความสำเร็จออกจากข้อผิดพลาด การไม่พบข้อมูลต้องไม่ถูกตีความว่า “ไม่มีปัญหา”

ฐานความรู้มีสี่เอกสารสั้น จึงเริ่มด้วย keyword matching เพื่อให้ตรวจสอบได้ง่าย ไม่ได้สร้าง vector database การค้นข้อมูลแล้วให้ LLM ใช้ข้อมูลนั้นประกอบคำตอบเป็น retrieval-augmented generation ได้ โดยวิธี retrieval ไม่จำเป็นต้องเป็นเวกเตอร์เสมอไป

หากต่อยอด semantic search จะเพิ่มขั้นเตรียมเอกสาร แบ่งข้อความ สร้าง embeddings และทำดัชนี จากนั้นเปลี่ยน implementation ของ search_knowledge_base โดยคงรูปแบบข้อมูลออกเดิมได้ match_score ปัจจุบันเป็นจำนวนคำที่ตรงกัน ไม่ใช่ความมั่นใจหรือโอกาสที่สาเหตุถูกต้อง

แบบฝึก: ถ้า search_knowledge_base ไม่พบเอกสารเลย agent ควรเสนอ auto_respond หรือเสนอให้ตรวจต่อ? มีข้อมูลอะไรที่อาจเปลี่ยนการตัดสินใจได้?

## Agent loop คือจุดที่โมเดลกับเครื่องมือทำงานร่วมกัน

เปิด `agent.py` แล้วไล่ TriageAgent.run:

1. แปลง ticket ทั้งบทสนทนาเป็น input ให้โมเดล พร้อม system prompt และ tool schemas
2. รับ output ถ้าเป็น function_call โมเดลกำลังขอให้โปรแกรมเรียกเครื่องมือ ยังไม่ใช่คำตอบสุดท้าย
3. ตรวจชื่อและ arguments แล้วเรียก ToolRegistry.call
4. ส่งผลกลับเป็น function_call_output โดยจับคู่ call_id
5. ส่ง conversation ที่เพิ่มข้อมูลกลับให้โมเดล ประวัติ output ทั้งหมดถูกเก็บไว้ รวมถึง reasoning items หากมี
6. หากเป็นคำตอบ JSON ให้ตรวจ Decision และแหล่งอ้างอิงก่อนยอมรับ
7. เพิ่ม approval state จากโค้ด แล้วคืนผลให้ terminal

ชื่อ call_id สำคัญเพราะใช้บอกโมเดลว่าผลนี้เป็นคำตอบของการเรียกเครื่องมือครั้งใด ไม่ใช่ข้อความลอย ๆ

ระบบจำกัดจำนวนรอบและ tool calls เพื่อไม่ให้โมเดลวนค้นไม่จบ เมื่อเกิด refusal, response ไม่ครบ หรือแก้ผลลัพธ์ไม่ผ่านภายในจำนวนรอบ จะคืน needs_human_review และ decision=null

แบบฝึก: หากโมเดลตอบทันทีโดยไม่เรียกเครื่องมือ โค้ดส่วนใดตรวจพบ และโมเดลได้รับข้อมูลอะไรเพื่อแก้ไข?

## System prompt และโค้ดรับผิดชอบคนละส่วน

เปิด `prompts/system.txt` กติกาประเมินผลกระทบ การอ่านข้อความทั้งหมด การไม่อ้างว่าแก้แล้ว และการตอบภาษาเดียวกับลูกค้าอยู่ที่นี่

ส่วนกติกาที่ตรวจแบบแน่นอนได้ เช่นรูปแบบ JSON, ticket ID, customer scope, แหล่งเอกสารที่มีจริง, critical ต้องเสนอ escalation และสถานะรออนุมัติ อยู่ในโค้ดด้วย

การทดสอบ GPT จริงครั้งแรกให้ระดับ high และเสนอส่ง billing ได้ แต่ตอบเป็นภาษาไทยทั้งที่ ticket เป็นอังกฤษ และสรุปยอดที่ลูกค้ารายงานเหมือนยืนยันธุรกรรมแล้ว เราจึงเพิ่มคำสั่งภาษาเฉพาะ ticket และตรวจ script ใน draft_reply ส่วนการอ้างธุรกรรมเพิ่มตัวอย่างประโยคที่แยก 'ลูกค้ารายงาน' ออกจาก 'เรายืนยัน' โดยยังไม่ถือว่าแก้ groundedness ครบทุกกรณี

การตรวจภาษาใน language.py เป็น heuristic สำหรับอังกฤษ/ไทยในโจทย์ ไม่ใช่ตัวตรวจภาษาทั่วไป และไม่สามารถแยกภาษาอังกฤษจากภาษาอื่นที่ใช้ตัวอักษรละตินได้ นี่เป็นตัวอย่างว่าต้องอธิบายขอบเขตของ guard ให้ตรงกับสิ่งที่โค้ดตรวจได้จริง

ต่อมาผลจริงพบว่าโมเดลใช้รหัสอ้างอิงไม่ตรงกับที่เครื่องมือคืนมา เราจึงเพิ่ม evidence.py ให้สร้าง schema ตามข้อมูลที่มีในแต่ละรอบ เช่น source=service_status ต้องใช้ reference เป็น region ที่ค้นจริง แทนการพิมพ์ URL ขึ้นมาเอง ส่วน customer_report ต้องคัดข้อความต้นฉบับตาม message ที่อ้างครบถ้วน เพื่อไม่ให้การสรุปเปลี่ยนรายงานยอดเงินเป็นหลักฐาน captured payment

ทำไมตรวจซ้ำใน Python เมื่อมี schema แล้ว? เพราะ schema ช่วยจำกัดสิ่งที่โมเดลสร้าง แต่โปรแกรมยังต้องยืนยันกติกาของตัวเองก่อนรับผล โดยเฉพาะกรณี input ยาวจนเราไม่ใส่ข้อความทั้งหมดใน enum ของ API โค้ดยังตรวจ exact quote ได้

reply.py ตรวจรูปแบบคำที่เราเห็นจากผลจริง เช่น “We are routing” หรือ “เราได้ส่งเรื่องแล้ว” เพราะไม่มีเครื่องมือส่งต่อจริง เมื่อไม่ผ่าน agent.py ส่งเหตุผลกลับให้โมเดลแก้ draft ด้วย tool results เดิม ไม่ต้องค้นใหม่เพื่อแก้รูปแบบอ้างอิง ทุกอย่างยังอยู่ภายในจำนวนรอบที่จำกัด

การตรวจนี้ไม่ได้อ่านความหมายได้ครบทุกประโยค คำอื่นที่สื่อว่าเริ่มตรวจสอบแล้ว หรือ summary ที่เพิ่ม captured payments ยังอาจหลุดได้ การอ้าง source ถูกกับการตีความ source ถูกจึงเป็นคนละเรื่อง ต้องมีการประเมิน groundedness และคนตรวจด้วย

## ทำไมใช้ agent เดียวก่อน

A วิเคราะห์และ B เขียนให้อ่านง่ายเป็นสองหน้าที่ แต่ยังไม่จำเป็นต้องเป็นสอง agent โปรแกรมนี้ให้โมเดลเดียวทำสองหน้าที่ผ่านผลลัพธ์ที่กำหนด การเพิ่ม agent จะเพิ่มค่าใช้จ่าย เวลา และจุดส่งต่อข้อมูล เราค่อยพิจารณาเมื่อทดสอบแล้วพบว่าการแบ่งบทบาทช่วยแก้ข้อผิดพลาดได้จริง

## อ่านผลสามเคสอย่างไร

ผล demo เป็นตัวอย่างตามนโยบายที่เราเลือก ไม่ใช่คำตอบเฉลยอย่างเป็นทางการของบริษัท

| เคส | ผลตัวอย่าง | เหตุผลหลัก |
|---|---|---|
| ชำระเงินซ้ำและยังไม่ได้ Pro | high และส่ง billing specialist | กระทบลูกค้ารายบุคคล มี deadline และความเสี่ยงข้อพิพาท แต่ยังไม่ยืนยัน captured charges |
| Enterprise เข้าไม่ได้ | critical และส่ง incident owner | เข้าถึงระบบหลักไม่ได้หลายคน มี demo ใกล้ถึงเวลา และข้อมูล status ขัดกับรายงานลูกค้า |
| Dark mode และตั้งเวลา | medium และส่ง product support | มี malfunction ที่ยังไม่จบ พร้อม feature request แยกกัน |

แบบฝึก: ทำไมไม่ใช้ sentiment เป็นตัวกำหนด urgency เพียงอย่างเดียว? ลองยกกรณีลูกค้าสุภาพแต่มีปัญหารุนแรง และลูกค้าโกรธแต่ไม่มีผลกระทบรุนแรง

## การทดสอบกับการประเมิน AI เป็นคนละเรื่อง

tests/test_triage.py ตรวจ flow และการรับมือ failure ด้วย model responses จำลอง ส่วน evaluate.py เป็น rubric เบื้องต้นของสามเคส เมื่อมี key ต้องรัน OpenAI mode แล้วตรวจผลทั้งอัตโนมัติและอ่านด้วยคน

สำหรับใช้งานจริงต้องมีชุดทดสอบที่ผู้เชี่ยวชาญตรวจคำตอบแล้ว และวัดทั้ง urgency, routing, extraction, retrieval, unsupported claims, latency และ cost ไม่ใช้ตัวเลข confidence ที่ LLM เขียนเองเป็นหลักฐานความถูกต้อง

## การตั้งค่าและผลจาก GPT จริง

ก่อนเรียก GPT โปรแกรมอ่านการตั้งค่าจากตัวแปรของ process หรือไฟล์ .env โดยใช้ triage/config.py การมีไฟล์ .env ไม่ได้ทำให้ Python อ่านเอง ต้องมี loader นี้รองรับ ค่าที่ตั้งใน terminal มีลำดับความสำคัญสูงกว่าไฟล์ เพื่อให้ key ที่ผู้ประเมินตั้งไว้ใช้งานได้ตามเดิม ส่วน .env ของผู้สมัครไม่รวมใน Git หรือ ZIP

คำสั่ง `& .\run.ps1 -Mode openai -CheckConfig` ตรวจว่ามี key ตั้งไว้และบอกแหล่งที่มา โดยไม่แสดงค่า key หรือส่งคำขอ API การผ่านคำสั่งนี้จึงยังไม่ยืนยันว่า key ถูกต้องหรือมีเครดิต ต้องทดสอบคำขอจริงแยกต่างหาก

ปัญหา credit_balance_exhausted ในช่วงแรกแก้จนเรียก GPT-4.1 mini ได้แล้ว ผลจริงสามเคสสร้างข้อเสนอได้ครบและใช้เครื่องมือ mock ผ่านโปรแกรมจริง แต่เราพบข้อผิดพลาดทั้งภาษา รหัสหลักฐาน และการอ้างว่าส่งต่อแล้ว จึงแก้ prompt ร่วมกับการตรวจในโค้ด รายละเอียดผลล่าสุดและข้อจำกัดอยู่ใน docs/verification.md

54 tests ที่ผ่านเป็นการทดสอบแบบออฟไลน์ ไม่ใช้เครดิต API และไม่ได้พิสูจน์ว่า GPT ตอบถูกทุกกรณี เช่น rubric อาจตรวจระดับกับ label ผ่าน แต่คนอ่านยังพบประโยคอ้างเกินข้อมูลได้ ก่อนส่งข้อความจริงต้องตรวจทั้งข้อมูลและสถานะการดำเนินการ

ผลรอบล่าสุดผ่าน rubric 3/3 แต่ summary เคสชำระเงินยังเพิ่ม captured ทั้งที่ unknowns ระบุว่ายังไม่ทราบ นี่คือความขัดแย้งที่ rubric ไม่ตรวจครบ เราเก็บ raw output แยกจากข้อความเสนอแก้ใน docs/live_review.md ไม่แก้ผลย้อนหลังแล้วอ้างว่าโมเดลสร้างได้ถูกเอง คุณควรเปิดทั้งสองไฟล์เทียบกันก่อนสัมภาษณ์

HTTP 429 ต้องดูประเภทเพิ่มเติม หากเป็น insufficient_quota หรือข้อจำกัด credits/spend/usage การรอแล้วเรียกซ้ำไม่แก้สาเหตุ แต่ถ้าเป็น rate limit ให้ลดอัตราคำขอและเคารพ Retry-After โปรแกรมจึงอ่าน error.code/type แล้วแสดงเฉพาะชื่อที่รู้จัก ไม่แสดง raw error message ที่อาจมีข้อมูลส่วนตัว และหยุด batch เมื่อควรแก้ API ก่อนประมวลผล ticket ต่อ

needs_human_review จาก API failure ไม่ได้แปลว่า AI ตัดสินให้ส่งเคสลูกค้าไปคนดูแล แต่หมายถึงระบบยังไม่ได้ข้อเสนอที่ใช้ได้ ต้องให้ผู้ดูแลตรวจเหตุขัดข้องก่อน decision จึงเป็น null ส่วน pending_human_approval เป็นนโยบายห้ามดำเนินการอัตโนมัติ ไม่ใช่หลักฐานว่ามีข้อเสนอพร้อมอนุมัติแล้ว

ก่อนส่งต้องอ่านคำอธิบายหนึ่งหน้าให้ตรงกับสิ่งที่คุณเข้าใจจริง และเตรียมอธิบายเหตุผลที่เลือกโครงนี้ ไม่จำเป็นต้องจำทุกบรรทัด แต่ควรอธิบายเส้นทางข้อมูลและข้อจำกัดได้
